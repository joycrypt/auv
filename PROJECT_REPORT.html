1. Executive Summary

This project implements a complete underwater navigation system for an Autonomous Underwater Vehicle (AUV). It estimates the vehicle's position, velocity, and orientation in real time by fusing five different sensors using an Extended Kalman Filter (EKF).

The system answers a fundamental question in robotics: "Where am I, how fast am I going, and which way am I pointing?" — using imperfect, noisy sensors that each measure only part of the picture.

What the system does (in plain words)

  • The IMU (accelerometer + gyroscope) runs fast (100 Hz) and predicts motion, but drifts over time.
  • The DVL (Doppler Velocity Log) measures velocity accurately but slower (10 Hz).
  • The Depth sensor measures how deep we are (2 Hz).
  • GPS/USBL gives absolute position but only near the surface and slowly (1 Hz).
  • The Magnetometer measures heading (5 Hz).

The EKF blends all of these optimally: it uses the fast IMU to predict, then corrects that prediction whenever a slower, more accurate sensor reports in. The result is a smooth, high-rate (100 Hz) estimate that does not drift.

2. Project Overview & Objectives

2.1 The Navigation Problem

Underwater, there is no continuous GPS — radio waves do not travel well through water. An AUV must therefore estimate its own state from onboard sensors. Each sensor alone is insufficient:

SensorStrengthWeakness
IMUVery fast (100 Hz), always availableIntegrates error → drifts without bound
DVLAccurate velocitySlower; occasional beam dropouts
DepthPrecise vertical positionOnly the Z axis
GPS/USBLAbsolute horizontal positionOnly near surface; slow; noisy
MagnetometerAbsolute headingOnly yaw; magnetic disturbance

2.2 The State Vector

The filter estimates a 9-element state vector x:

x = [ px, py, pz, vx, vy, vz, φ(roll), θ(pitch), ψ(yaw) ]ᵀ
IndexSymbolMeaningUnits / Frame
0pxPosition Northm (NED nav frame)
1pyPosition Eastm (NED nav frame)
2pzPosition Down (depth)m (positive = deeper)
3vxVelocity Xm/s
4vyVelocity Ym/s
5vzVelocity Zm/s
6φ rollRotation about Xrad
7θ pitchRotation about Yrad
8ψ yawRotation about Z (heading)rad
Coordinate frames: The navigation frame is NED (X=North, Y=East, Z=Down). The body frame is fixed to the vehicle (X=bow/forward, Y=starboard, Z=keel-down). The rotation matrix Rbn converts body-frame vectors into the navigation frame.

4. The Data Pipeline — How the Test Data is Created

Because real sea-trial data is not always available, the project includes a synthetic data generator (CSVParser::generateSyntheticData). It simulates a "true" vehicle trajectory, then produces realistic noisy sensor readings from that ground truth. This is run with ./auv_nav2 --generate-data.

4.1 The Simulated Mission (4 Phases, 80 seconds)

The generator advances a true state with Euler integration at 100 Hz and switches behaviour by time phase:

PhaseTimeBehaviourCommanded motion
1. Descent + Surge0–20 sNose pitches down to about −10°, accelerates forwardax≈0.4 m/s² (decaying), gy = −0.008 rad/s
2. Banked Turn20–40 sRolls to ~20° bank and yaws (turning)gz = 0.04 rad/s, gx = 0.005
3. Level Cruise40–60 sRoll & pitch return to 0, steady cruiseno commanded acceleration
4. Ascent60–80 sPitches up to ~+8.6°, deceleratesax < 0 (braking), gy = +0.008

4.2 The Ground-Truth Kinematics

The "true" vehicle obeys exactly the same physics the EKF assumes — this lets us measure how well the filter recovers the truth. Each 0.01 s step:

v_nav += ( Rbn · a_body − [0, 0, g] ) · dt (g = 9.81) p_nav += ( Rbn · v_body ) · dt η += W(φ,θ) · ω_body · dt (then wrapped to [−π, π]) if pz < 0: pz = 0, vz = 0 (cannot fly above the surface)

4.3 The Sensor Models (Truth + Noise)

From the true state, each sensor reading is synthesized by adding Gaussian noise and applying realistic limitations. A fixed RNG seed (2024) makes the dataset reproducible.

SensorRateHow it is generatedNoise σ
IMU accel100 HzMeasures specific force = a_body + gravity projected into body axes:
ax = ax_b + g·sinθ; ay = ay_b − g·cosθ·sinφ; az = az_b − g·cosθ·cosφ		0.05 m/s²
IMU gyro100 HzTrue body rates gx_b, gy_b, gz_b + noise0.003 rad/s
DVL10 HzTrue nav velocity rotated into body frame (Rᵀ·v) + noise; 5% random dropout (valid=0)0.02 m/s
Depth2 Hzmax(0, pz + noise)0.05 m
GPS/USBL1 Hzpx, py + noise; valid only when pz < 2 m (submerged → no fix)1.5 m
Mag5 HzTrue yaw + noise0.02 rad
Key subtlety — the gravity term. A real accelerometer cannot separate gravity from motion; it measures specific force. So when the AUV is level, the accelerometer reads about −9.81 on the Z axis. The EKF's prediction step must therefore subtract gravity to recover true acceleration. This is exactly why the generator adds the gravity projection, and why stateTransition later subtracts g.
Why GPS goes invalid below 2 m. This models reality: once the AUV dives past 2 m the GPS/USBL fix is lost. During those periods the filter must rely on IMU + DVL + Depth only. This is what makes the position uncertainty plot (Group 5) so instructive — you can see σ grow while submerged and snap down when GPS returns near the surface.

6. The Matrix Library (matrix.hpp)

The EKF needs linear algebra (multiply, transpose, invert). Rather than depend on a library like Eigen, the project includes a small, header-only, fixed-size matrix class. The size is part of the type (Matrix<R,C>), so dimension mistakes are caught at compile time.

6.1 What it provides

OperationMethodUsed for
Element access(r,c) or [i]Reading/writing entries
Add / subtract+ - +=P + Q, z − Hx
Scalar multiply* Scaling by dt
Matrix multiplyA * BF·P, H·P·Hᵀ
Transpose.transpose()Fᵀ, Hᵀ

Clamp diagonal.clampDiagonal(min)Keep P positive-definite

6.2 The Inverse (Gauss-Jordan with Partial Pivoting)

The matrix inverse is the most delicate operation. It uses Gauss-Jordan elimination: augment with the identity, then row-reduce. Partial pivoting (swapping in the row with the largest pivot element) improves numerical stability. If a pivot is essentially zero, the matrix is singular and an exception is thrown — a useful early warning that noise parameters are misconfigured.

Type aliases used throughout: Vec9 = Matrix<9,1> state vector Mat9 = Matrix<9,9> covariance, Jacobian Mat3x9 = Matrix<3,9> DVL observation matrix H Mat9x3 = Matrix<9,3> Kalman gain K (for a 3-D measurement)

7. EKF Theory & Mathematics

7.1 Why "Extended"?

A standard Kalman Filter assumes the system is linear: xk = A·xk−1 + B·u. But our motion model is nonlinear — the rotation matrix Rbn and the Euler kinematics matrix W contain sines, cosines, and tangents of the attitude angles. The Extended KF handles this by linearising the model at each step: it computes the Jacobian (matrix of partial derivatives) F = ∂f/∂x around the current estimate.

7.2 The Two Phases

┌──────────────── PREDICT (every IMU step, 100 Hz) ────────────────┐ │ x⁻ = f(x, u, dt) propagate state with IMU │ │ F = ∂f/∂x linearise (Jacobian) │ │ P⁻ = F·P·Fᵀ + Q grow uncertainty │ └──────────────────────────────────────────────────────────────────┘ ┌──────────────── UPDATE (when a sensor reports) ──────────────────┐ │ y = z − H·x⁻ innovation (measurement − predict) │ │ S = H·P⁻·Hᵀ + R innovation covariance │ │ K = P⁻·Hᵀ·S⁻¹ Kalman gain (optimal blend) │ │ x = x⁻ + K·y correct the state │ │ P = (I−KH)P⁻(I−KH)ᵀ + KRKᵀ shrink uncertainty (Joseph form) │ └──────────────────────────────────────────────────────────────────┘

7.3 The Motion Model f(x, u, dt)

Position: ṗ = Rbn(φ,θ,ψ) · v_body Velocity: v̇ = Rbn(φ,θ,ψ) · a_body − [0, 0, g]ᵀ Attitude: η̇ = W(φ,θ) · ω_body

Rotation matrix Rbn (ZYX: yaw → pitch → roll)

Rbn = [ cψcθ cψsθsφ−sψcφ cψsθcφ+sψsφ ] [ sψcθ sψsθsφ+cψcφ sψsθcφ−cψsφ ] [ −sθ cθsφ cθcφ ] where c = cos, s = sin

Euler kinematics matrix W(φ,θ)

W = [ 1 sinφ·tanθ cosφ·tanθ ] [ 0 cosφ −sinφ ] [ 0 sinφ/cosθ cosφ/cosθ ] (singular at θ = ±90° — "gimbal lock"; guarded in code)

7.4 The Tuning Parameters

The filter behaviour is controlled by noise standard deviations. Smaller σ = trust that source more.

ParameterValueMeaning
sigma_acc0.02Accelerometer noise (m/s²)
sigma_gyro0.001Gyroscope noise (rad/s)
sigma_dvl0.02DVL velocity noise (m/s)
sigma_depth0.01Depth noise (m)
sigma_gps0.5GPS/USBL position noise (m)
sigma_mag0.015Magnetometer yaw noise (rad)
sigma_proc0.01Process model noise (how much we distrust the model)

8. Code Walkthrough — How the Code Works

8.1 main.cpp — The Orchestrator

The main() function ties everything together in six steps:

  1. Parse arguments — optional file paths, --generate-data, --verbose.
  2. (Optional) generate synthetic data if --generate-data is passed.
  3. Load all five sensor files via CSVParser.
  4. Construct and initialise the EKF with the tuned noise parameters.
  5. Run the fusion loop (the heart of the program).
  6. Save results and print a mission summary.

The Fusion Loop

This is the core control flow. For every IMU sample it predicts, then applies whichever sensor measurements have "come due" (timestamp ≤ current IMU time):

for (size_t i = 1; i < imu_data.size(); ++i) { double dt = imu.timestamp - imu_data[i-1].timestamp; if (dt <= 0.0 || dt > 1.0) continue; // skip bad timestamps ekf.predict(imu, dt); // 1. PREDICT with IMU while (dvl[i_dvl].timestamp <= imu.timestamp) ekf.updateDVL(...); // 2. while (dep[i_dep].timestamp <= imu.timestamp) ekf.updateDepth(...); // 3. while (gps[i_gps].timestamp <= imu.timestamp) ekf.updateGPS(...); // 4. while (mag[i_mag].timestamp <= imu.timestamp) ekf.updateMag(...); // 5. NavState ns = ekf.getNavState(imu.timestamp); // record the result results.push_back(ns); }
Why the while loops? Sensors run at different rates. Between two IMU samples (0.01 s apart), zero or more DVL/depth/GPS/mag samples may have arrived. The while drains every measurement that is now due, so each is applied exactly once at the right time. The index counters (i_dvl etc.) never rewind, giving an efficient single pass over all data.

8.2 ekf.cpp — The Filter

8.2.1 initialise()

Sets the starting state. Roll and pitch are bootstrapped from the accelerometer (which senses the gravity direction when nearly static); yaw comes from the magnetometer; depth and velocity from their sensors. The initial covariance P₀ encodes how confident we are in that starting guess.

pitch = asin(-ax / |a|); roll = atan2(ay, az); // from gravity vector yaw = initial_yaw_rad; // from magnetometer P0 = diag([1,1,1, 0.04,0.04,0.04, 0.005,0.005,0.05]);

8.2.2 predict()

Runs once per IMU step. It (a) propagates the state through the nonlinear model, (b) builds the Jacobian F, (c) builds process noise Q for this dt, and (d) propagates the covariance.

x_ = stateTransition(x_, ax,ay,az, gx,gy,gz, dt); // nonlinear propagate Mat9 F = computeJacobian(x_, ax,ay,az, gx,gy,gz, dt); Mat9 Q = buildQ(dt); P_ = F * P_ * F.transpose() + Q; // covariance grows P_.clampDiagonal(1e-9); // numerical guard

8.2.3 stateTransition() — the nonlinear model

Implements the equations from §7.3: rotate body velocity/acceleration into the nav frame, subtract gravity from the Z acceleration, integrate position/velocity, and integrate attitude with the W matrix. Angles are wrapped to [−π, π].

8.2.4 computeJacobian() — linearisation

F is a 9×9 matrix of partial derivatives. The non-trivial blocks come from differentiating Rbn and W with respect to the attitude angles. The code computes these analytically (exact derivatives dR/dφ, dR/dθ, dR/dψ, and dW/dφ, dW/dθ) rather than numerically — faster and more accurate.

F structure (block form): ∂ṗ/∂v = Rbn·dt ∂ṗ/∂η = (∂R/∂η·v)·dt ∂v̇/∂η = (∂R/∂η·a)·dt ∂η̇/∂η = I + (∂W/∂η·ω)·dt

8.2.5 buildQ() — process noise

Q models how much real motion deviates from our idealised model in time dt. It uses the standard continuous-to-discrete (Van Loan) conversion for a position–velocity system, which correctly couples position and velocity noise:

Q(pos,pos) = qvel · dt⁴/4 // position variance from velocity noise Q(pos,vel) = qvel · dt³/2 // position-velocity correlation Q(vel,vel) = qvel · dt² // velocity variance Q(att,att) = qatt · dt² // attitude variance

8.2.6 ekfUpdate<M>() — the generic correction

A single templated function handles all sensors. M is the measurement dimension (1 for depth/mag, 2 for GPS, 3 for DVL). It computes the innovation, the gain, updates the state, and updates the covariance in Joseph form for stability:

y = z - H * x_; // innovation S = H * P_ * H.transpose() + R; // innovation covariance K = P_ * H.transpose() * S.inverse(); // Kalman gain x_ = x_ + K * y; // state correction IKH = I - K*H; P_ = IKH * P_ * IKH.transpose() + K * R * K.transpose(); // Joseph form

8.2.7 The five sensor updates

MethodMeasuresH picks state indexDim
updateDVLvx, vy, vz3, 4, 53
updateDepthpz21
updateGPSpx, py0, 12
updateMagyaw81

The magnetometer update is special: it computes the innovation with angle wrapping so that, e.g., 179° and −179° are treated as 2° apart, not 358°.

8.2.8 getNavState() — assembling output

Copies the state into a NavState, converts attitude to convenient forms, computes derived quantities (horizontal speed, total speed, cumulative distance), and reports per-group 1σ uncertainties from the diagonal of P:

std_pos_m = sqrt( (P[0,0]+P[1,1]+P[2,2]) / 3 ) std_vel_ms = sqrt( (P[3,3]+P[4,4]+P[5,5]) / 3 ) std_att_deg = sqrt( (P[6,6]+P[7,7]+P[8,8]) / 3 ) · 180/π

9. Complete Manual Calculation (One Full Cycle)

This section works one EKF cycle by hand so the math is fully transparent. We use representative values around t = 0.32 s.

9.1 Starting Point

StateValue
Position [px, py, pz][−1.30, 1.80, 0.09] m
Velocity [vx, vy, vz][0.10, 0.05, 0.02] m/s
Attitude [φ, θ, ψ][−3.122, 0.007, 0.304] rad ≈ [−178.9°, 0.4°, 17.4°]
P (diagonal) = [1.0, 1.0, 1.0, 0.04, 0.04, 0.04, 0.005, 0.005, 0.05] IMU input: a = [0.12, −0.03, 9.85] m/s², ω = [−0.001, 0.025, −0.002] rad/s, dt = 0.01 s

9.2 PREDICT — Step by Step

Step 1: Rotation matrix Rbn

cosψ=0.954, sinψ=0.299, cosθ≈1.000, sinθ=0.007, cosφ≈−1.000, sinφ=−0.020 Rbn ≈ [ 0.954 0.299 0.001 ] [ −0.299 0.954 0.007 ] [ −0.007 0.000 1.000 ]

Step 2: Velocity update (rotate accel, subtract gravity)

a_nav = Rbn · [0.12, −0.03, 9.85]ᵀ = [0.105, −0.051, 9.849] subtract g: a_nav_z = 9.849 − 9.81 = 0.039 vx = 0.10 + 0.105×0.01 = 0.101 m/s vy = 0.05 + (−0.051)×0.01 = 0.049 m/s vz = 0.02 + 0.039×0.01 = 0.020 m/s

Step 3: Position update (rotate velocity)

v_nav = Rbn · [0.10, 0.05, 0.02]ᵀ = [0.110, 0.018, 0.020] px = −1.30 + 0.110×0.01 = −1.299 m py = 1.80 + 0.018×0.01 = 1.800 m pz = 0.09 + 0.020×0.01 = 0.090 m

Step 4: Attitude update (W · ω)

dη = W(φ,θ) · [−0.001, 0.025, −0.002]ᵀ · dt = [−0.000018, 0.000250, −0.000020] roll = −3.122 + (−0.000018) ≈ −178.96° pitch = 0.007 + 0.000250 ≈ 0.41° yaw = 0.304 + (−0.000020) ≈ 17.42°

Step 5: Covariance grows

P⁻ = F · P · Fᵀ + Q With sigma_proc = 0.01 and dt = 0.01: Q is tiny (Q_vel ≈ 1e-8), so P barely grows in one step.

9.3 UPDATE — DVL Measurement Arrives

The DVL reports body velocity z = [0.10, 0.05, 0.02] m/s.

Innovation: y = z − H·x⁻ = [0.10,0.05,0.02] − [0.101,0.049,0.020] = [−0.001, 0.001, 0.000] Innovation cov: S = P_vel + R_dvl = 0.04 + 0.0004 = 0.0404 (per axis) Kalman gain: K = P_vel / S = 0.04 / 0.0404 = 0.990 (trust DVL ~99%) State correction: vx = 0.101 + 0.990×(−0.001) = 0.100 m/s vy = 0.049 + 0.990×( 0.001) = 0.050 m/s vz = 0.020 + 0.990×( 0.000) = 0.020 m/s Covariance shrinks (Joseph): P_vel⁺ = (1−0.990)²·0.04 + 0.990²·0.0004 ≈ 0.00043 σ_vel = √0.00043 ≈ 0.021 m/s (was 0.2 m/s)

9.4 UPDATE — Depth Measurement Arrives

z_depth = 0.09 m, predicted pz = 0.090 m Innovation y = 0.09 − 0.090 = 0.000 m (perfect match) S = P_pz + R_depth = 1.0 + 0.0001 = 1.0001 K = 1.0 / 1.0001 ≈ 0.9999 (trust depth almost completely) σ_pz⁺ = √0.0001 = 0.01 m (was 1.0 m)

9.5 Interpreting the Kalman Gain

Gain KMeaningWhen
≈ 1.0Trust the measurementSensor very accurate OR prediction uncertain
≈ 0.5Balance bothComparable uncertainties
≈ 0.0Trust the predictionSensor noisy OR prediction confident

The gain is literally K = (prediction uncertainty) / (prediction + measurement uncertainty). Our DVL gain of 0.99 says: "the prediction has σ=0.2 m/s, the DVL has σ=0.02 m/s, so weight the DVL heavily."

Group 1 — Position (px, py, pz)

The roll "180°" display trick. Euler angles are ambiguous: an orientation can be written as (φ, θ, ψ) or (φ±180°, 180°−θ, ψ±180°). The vehicle starts nearly inverted in roll (≈−179°), so the visualizer maps values near ±180° back toward 0 for a readable plot. This is a display choice only — the filter math is unaffected.

Group 4 — Derived (speed_horiz, speed_total, distance, depth)

Left: quantities computed directly from raw DVL — horizontal speed √(vx²+vy²), total speed, and DVL-only dead-reckoning distance (which drifts because there is no position correction). Right: the EKF's equivalents, including the cumulative path odometer that always increases.

Group 5 — Uncertainty (std_pos, std_vel, std_att)

This is the most insightful figure. Left: a simulated "what if we had no EKF" curve — dead-reckoning error growing without bound (position ∼ t1.5, velocity and attitude linear in t). Right: the actual EKF σ from the covariance matrix, which converges and stays low. Faint vertical lines mark DVL/Depth/GPS/Mag update events, so you can literally see σ drop each time a sensor corrects the filter.

Left-panel drift models (illustrative, drawn in the script): position drift ≈ σ₀ + 0.005 · t1.5 velocity drift ≈ σ₀ + 0.0008 · t attitude drift ≈ σ₀ + 0.04 · t

10.4 Why the Comparison Matters

The left-vs-right layout is the project's main visual argument: raw sensors are jumpy, sparse, and (for dead-reckoning) divergent; the EKF output is smooth, continuous at 100 Hz, and bounded in uncertainty. The figures are the evidence that the fusion is working.

12. Questions & Answers

Q1. What problem does this project solve?
It estimates an AUV's position, velocity, and orientation underwater, where GPS is unavailable, by optimally fusing five complementary sensors with an Extended Kalman Filter.
Q2. Why an EKF and not a plain Kalman Filter?
The motion model is nonlinear — the rotation matrix and Euler kinematics use sin/cos/tan of the attitude angles. The EKF linearises the model at each step by computing the Jacobian F = ∂f/∂x, allowing the linear KF equations to be applied.
Q3. What does the "predict" step do, intuitively?
It uses the fast IMU to guess where the vehicle moved in the last 0.01 s (integrating acceleration into velocity and velocity into position, plus gyro into attitude). Because integration accumulates error, this step also grows the uncertainty P.
Q4. What does the "update" step do?
When a slower, more accurate sensor reports, the filter compares it to the prediction (the "innovation"), computes a Kalman gain that weights the two by their relative trust, nudges the state toward the measurement, and shrinks the uncertainty.
Q5. What is the Kalman gain physically?
A number between 0 and 1 (per dimension) equal to prediction-uncertainty / (prediction + measurement) uncertainty. Near 1 means "trust the sensor"; near 0 means "trust the model". For our DVL it is about 0.99.
Q6. Why does GPS disappear in the middle of the mission?
The simulator marks GPS invalid whenever depth > 2 m, modelling loss of fix while submerged. During those times the filter relies on IMU + DVL + Depth, and the position uncertainty visibly grows until GPS returns near the surface.
Q7. Why does the accelerometer read ~−9.8 when level?
An accelerometer measures specific force, which includes gravity. The prediction step subtracts gravity (in the navigation frame) to recover the true motion acceleration.
Q8. What is the Joseph form and why use it?
It is the numerically stable form of the covariance update, P = (I−KH)P(I−KH)ᵀ + KRKᵀ. It guarantees P stays symmetric and positive-definite even with rounding errors, preventing the filter from diverging.
Q9. Why is the roll near ±180° in the data?
Euler angles have a representation ambiguity. The vehicle starts nearly inverted in roll, so the filter reports values near ±180°. The visualizer remaps these toward 0 purely for readability — the underlying orientation is correct.
Q10. How are the graphs produced?
The Python script reads nav_output.csv and the raw data/*.csv with Pandas, then draws five Matplotlib figures. Each figure puts raw sensor data on the left and the smooth EKF estimate (with a ±1σ band and sensor-update markers) on the right.
Q11. What does Group 5 (uncertainty) prove?
It contrasts unbounded dead-reckoning drift (left) against the EKF's converged, bounded uncertainty (right). The vertical event lines show σ dropping each time a sensor corrects the filter — direct evidence the fusion works.
Q12. How would you verify the filter is correctly tuned?
Check innovation consistency: the innovations y should be zero-mean and statistically consistent with their predicted covariance S (a chi-squared / "whiteness" test). Persistently large innovations mean R or Q is too small; persistently tiny ones mean they are too large.
Q13. Could a more advanced filter do better?
Yes — an Unscented Kalman Filter (UKF) avoids explicit Jacobians and handles strong nonlinearity better, and a particle filter handles arbitrary distributions. For this AUV, the EKF is an excellent trade-off of accuracy, speed, and simplicity.
